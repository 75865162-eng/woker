# Wimoor vs 我方（tiaotiao / woker）功能差距与移植计划

> 日期：2026-11-23
> 性质：只读调查 + 移植规划（未改业务代码、未连生产库写入）
> 基准仓库：`wimoor-erp/wimoor`（clone 到 `/workspace/wimoor`，浅克隆，1393★）
> 我方仓库：`/workspace/woker`（Next.js 15 + Prisma 7 + PostgreSQL）
> 对比口径：**排除亚马逊页面**（wimoor 的 `views/amazon/**`、`wimoor-amazon*`、`wimoor-amazon-adv`，以及我方 `/amazon/**` 全部路由），只比通用 ERP 业务能力。

---

## 0. 结论先行

1. **双方不是同一类系统的差距，而是两种定位**：wimoor 是**可写的业务操作系统**（采购/仓库/发货/财务均有审批流、状态机、打印、导入导出）；我方 woker 是**外部数据源只读快照 + 本地核心主档 + 部分本地协同写操作**的数据洞察平台。
2. **我方财务能力不弱反强**：已具备完整复式记账、期末结账、禁自审/独立关账复核/并发锁，比 wimoor 更严谨；仅缺「现金流量表 / 权益变动」标准报表模板。
3. **真正的差距集中在三块**：① 供应链业务闭环（发货/海外仓/生产制造的写操作与状态机）；② 基础主数据的完整度（辅料包材、SKU 配对、质检）；③ 我方 `data-plan.ts` 中 **28 个 `planned` 未接入的数据源/页面**。
4. **移植必须分两类**：wimoor 的 OPERATE 类功能不能直接照搬到只读快照体系；应优先补齐「我方已规划但未接入（planned）」的读模型，再评估少量确有必要本地化的写功能。

## 4. 移植策略（关键原则）

### 4.1 不照搬 OPERATE 写系统

wimoor 是「可写业务操作系统」，我方架构红线（`AGENTS.md`）明确：
- 外部快照/Projection/Read Model **不得反向覆盖核心主档**；
- 缺失数据保留 null / NEEDS_DATA，**不造数**；
- 研究/建议/广告草稿**不自动写入**商品/上架/投放。

因此移植分两类：
- **A 类（读模型移植，优先）**：把我方 `data-plan.ts` 中 planned 的数据源按既有「通用采集器 + typed 表 + 只读工作台」模式接入。与现有架构一致、风险低、验收清晰。
- **B 类（写功能本地化，审慎）**：海外仓/生产/发货单的写操作，只有当确认要在我方系统内**管理这些业务**（而非仅查看）时才做，需独立设计状态机、审批、审计，属于新业务线，不可当作"补齐功能"轻率移植。

### 4.2 移植顺序（每阶段独立可验收）

| 阶段 | 内容 | 依赖 | 验收标准 |
| --- | --- | --- | --- |
| S1 | P0 数据源接入（6 项） | 赛狐 API 凭据（已配于服务器） | 通用采集器实测有真实行数；typed 表字段按 payload 定型；只读工作台可查；金额转 Decimal 三列 |
| S2 | 财务报表补齐（现金流量/权益变动） | 现有 finance report service | 模板 kind 扩展；基于 POSTED_LEDGER 渲染；单测锁定借贷/合计 |
| S3 | P1 读模型补齐（库存单据/出入库/采购链/付款） | S1 模式复用 | 同上；不混用事实源 |
| S4 | B 类评估与决策 | 产品/业务方确认是否要写 | 输出 go/no-go 结论；若 go，单独立项目 |

## 5. 风险与未知

- **未知 U1**：wimoor 菜单 SQL 是某一历史快照，可能不含最新功能；以 clone 源码为准交叉验证过 views 目录。
- **未知 U2**：我方 `data-plan.ts` 的 planned 项状态是代码快照，实际服务器运行版本是否仍 planned 需在服务器侧复核（源码已确认三方一致 `af8f453a`）。
- **风险 R1**：赛狐 API 未存档的端点（标注"文档：xxx"）需真实凭据试调确认字段，禁止臆造 typed 表。
- **风险 R2**：生产/海外仓写功能移植会引入新事实源，必须遵守"不覆盖核心主档"红线，需产品侧决策。
- **范围**：本报告已按要求排除亚马逊页面；若需要亚马逊部分对比，另立报告。
