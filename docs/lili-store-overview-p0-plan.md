# Lili MCP 店铺经营概览 P0 核对与方案

## 目标与范围

以一个已授权卖家和站点为范围，查询上一个完整自然周和前一周的销售日报、同步状态及覆盖证据，输出来源、业务时区、币种、数据时间、缺失情况和可追溯结果。商品级变化仅在存在可验证的商品级数据及覆盖证据时提供，否则说明无法判断。此阶段只读，不申请同步或修改店铺。

## 当前代码核对

| 场景 | 参考能力 | 当前代码证据 | 缺口与优先级 |
| --- | --- | --- | --- |
| 连接和身份 | 用户连接 MCP，选择授权店铺 | `src/lib/lili/research-bearer-server.ts` 使用 Amazon MCP 凭证认证；`src/lib/lili/runtime-server.ts` 复用 Amazon MCP 调用器；OAuth 另见 `src/lib/lili/oauth.ts` | 实际环境连接及授权须端到端核验；P0 |
| 店铺销售 | 店铺与日期范围销售查询 | `src/lib/amazon-sync/mcp.ts` 的 `amazon.sales.list` 调用页面同用的 `readSalesTraffic`；`sales-query.ts` 使用实时账号授权 | 返回店铺逐日数据和分页，但未形成上周经营概览合同；P0 |
| 数据健康 | 同步进度与覆盖 | `data_sync_status` 调用 `readSyncCoverage`，返回运行及覆盖证据 | 历史覆盖不自动证明指定周完整，需核验目标周；P0 |
| 商品变化 | 按商品比较销售 | Amazon 销售日报明确为 `SELLER_DAY`；`src/lib/sellfox/mcp-tool-registry.ts` 列出赛狐商品日销 | Amazon 店铺日报不能推断商品销量；赛狐需独立核验身份映射、授权和完整性，P0 缺证据时返回未知 |
| 工作流 | 周经营复盘提示词 | `src/lib/lili/catalog.ts` 加载已发布模板和技能；参考原文位于用户文档目录的多宝鱼工作流模板 | 已有模板是定义，不能证明每个步骤已实现；需增加基于实际工具的 P0 指引 |
| 草稿及执行 | 建议预览与受控动作 | `src/lib/amazon-sync/mcp.ts` 的 `data_sync_start` 创建审批申请，不直接启动 | 本次不扩展写入或执行；P2 |
| 广告、财务及库存 | 多域经营分析 | 目录和各域实现分别存在 | 未逐项验证，不能视为已闭环；P1/P2 |

上述结论来自当前代码静态核对，不代表服务端授权、数据完整或生产已验收。多宝鱼工具清单和 12 个模板仅作场景参考。

## 拟实施方案

1. 在 Amazon 统一查询层扩展一个有界只读经营概览服务：显式要求卖家、站点及业务日期范围；复用 `readSalesTraffic`、已有站点时区和覆盖证据，不新增数据库事实源。当前周与对比周逐日核对：没有充分完整性证据时标记未知或部分，不用零补缺。
2. 在现有 Amazon MCP 注册并调用该服务，由 Lili 已有 ERP 通道暴露；认证、实时店铺权限与审计继续使用原有机制。返回业务范围、来源、时区、币种、日期、行数据、覆盖/缺口、同步时间和比较是否可用；金额采用字符串。商品级结果先返回未具备可靠证据的明确状态，不拼接无身份映射的赛狐数据。
3. 在现有 Lili 工作流目录增加与实际工具一致的操作指引，说明参数、缺失处理、结果格式和只读边界。
4. 扩展相关单测与隔离 MCP 集成测试：正常、缺日、跨币种、分页边界、无授权、跨组织、撤权、错误与审计；核对 ERP 与 MCP 同一服务的结果。测试不连接真实店铺。

## 影响、回退和验证

预计触及 `src/lib/amazon-sync/` 查询服务及 MCP 注册/分发、`src/data/lili/` 工作流定义和相关测试；不会主动修改数据库 schema、凭据、后台计划或同步任务。新增工具和工作流改变对外 MCP 目录与返回合同，需按仓库规则先确认。性能上限制单卖家、单站点和日期范围，避免首屏查询及无界全表读取；隔离测试检查查询边界。

代码回退为移除新增工具、服务和工作流并发布已验证的前一应用版本；不回滚数据库。具体生产部署由 CI artifact 和 deployment-plan 决定，迁移、依赖、服务器基线与所有拟发布提交在操作前重新核对。服务器验收只读核对实际身份、工具发现、授权范围、指定日期覆盖与查询结果；数据不足时如实报告，不把健康检查等同业务通过，也不自行启动真实同步。

当前工作树已有未提交的性能记录、构建目录和报告；当前分支相对本地记录的 `origin/tiaotiao-erp` 多 31 个历史提交。它们是否已经发布以及哪些属于本次上线须对照 GitHub 和线上 release 实际状态，不能单凭分支领先数量判断。
