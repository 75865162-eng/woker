# Amazon 账号级数据访问统一改造规划

日期：2026-11-10。状态：规划，尚未实施或真实验收。

## 1. 目标与适用范围

采用用户本次确定的最终规则：ERP 用户被分配一个 Amazon Seller Account 后，自动取得该账号全部已接入业务数据的 ERP / MCP / Lili 读取能力。账号范围是唯一的 ERP 内部 Amazon 数据读取授权维度；不再叠加字段、指标、表、API、数据域、广告模块或站点的内部读取授权。

保留可信用户身份、组织和工作空间归属、账号分配、Amazon 官方授权条件、秘密保护、审计及真实写操作人工审批。组织和 Workspace 仍是租户边界，Marketplace 是数据筛选及官方授权维度，不再是另一套用户授权。

本规划基于当前工作目录（含已有未提交改动）的定向源码调查，不代表服务器版本或数据库现状。没有连接真实数据库、调用 Amazon、变更配置、启动任务或执行迁移。本轮只新增本文。

仅调整 Amazon 账号业务数据权限；不把商品中心 ProductRecord、PPC 原始文件、外部 SellerSprite 研究服务或系统管理操作一并开放。读取权限不授予管理凭证、分配账号、修改主档、同步配置或执行广告写入的权限。

## 2. 当前代码与目标差异

| 已确认入口 | 当前实现 | 改造方向 |
| --- | --- | --- |
| `src/lib/amazon-sync/data-access.ts` | 叠加模块 action、个人/角色 grant、marketplaceIds、mcpEnabled；ERP 管理员可直接 allSellers | 统一按当前用户有效账号分配解析读取范围；包括管理员业务查询在内均不能隐式读取未分配账号 |
| `prisma/schema.prisma` / `access-management.ts` | AmazonDataAccessGrant 已有 user→seller 唯一关系；另有角色授权及操作、站点、MCP 开关 | 复用个人账号分配表；读取不再依赖细粒度配置，管理和写审批独立保留 |
| `src/lib/amazon-sync/mcp.ts` | 凭证保存 tools/scopes，与实时 ERP grants 再取交集；部分授权异常被归为认证失败 | 凭证证明用户身份，Amazon 读取工具随账号自动可用；账号范围每次从服务端解析，分别返回身份/账号/官方授权/数据错误 |
| `src/lib/lili/account-tool-access.ts` | 普通凭证使用工具清单；有效 Lili OAuth device 可继承已注册工具 | 将 Amazon 只读工具统一继承；外部研究和写工具不因本次改造自动扩权 |
| `src/lib/lili/runtime-server.ts` | ERP 会话调用依赖既有个人 MCP 凭证；无凭证或多个凭证会阻断/要求选择 | ERP 内嵌 Lili 直接使用当前会话身份进入同一网关；外部客户端保留个人 OAuth/Token 认证 |
| `finance-query.ts` / `data-access.ts` | 财务只限管理员；sourceAccessWhere 对非 allSellers 排除 finance/notifications | 已分配账号的财务、通知等读取继承账号权限；保留官方能力、来源归属与秘密保护 |
| `src/lib/amazon-sync/mcp.ts` 的 adsEntityFields | 固定字段白名单会缩减已存储广告 payload | 共享业务序列化器提供完整已接入字段，扩展字段不静默丢弃 |
| `src/lib/amazon-ads/query-service.ts` / `data-query.ts` | 已有查询服务/Repository，但 ERP、MCP 尚有不同组合与投影 | 收敛到现有共享查询边界，统一过滤、序列化、来源和错误，不新建第二套查询系统 |
| `sp-api-datasets.ts` / `dataset-query.ts` / 字段注册相关实现 | 工具/表/字段合同、数据可用性及旧权限说明并存 | 区分 Schema、能力状态与用户权限；登记表不能充当逐用户表权限 |
| `src/lib/amazon-sync/mcp-scope.ts` | 业务查询已要求单账号+单站点；账号发现例外 | 保留单账号强约束；站点参数作为查询语义保留，卖家级数据支持单账号查询 |
| `src/lib/amazon/ads-client.ts` | 真实 Ads 写入 transport 明确 NOT_IMPLEMENTED | 云端真实执行是独立待完成交付，不通过删开关或放宽读取冒充实现 |

本轮没有发现可据以认定“全仓存在统一字段 ACL 表”的证据。已确认的问题同时包含权限叠加和固定投影，实施时逐项追踪，不能把所有白名单都当作权限代码删除。

## 3. 目标调用链与判定

```text
ERP 会话 / 外部 MCP 用户凭证
              ↓ 可信 userId + organizationId + workspaceId
ERP API / 原生 MCP / Lili → 现有服务端统一查询服务
              ↓ 实时读取用户→SellerAccount 分配
              ↓ 校验本次唯一账号及相应官方授权状态
              ↓ Repository（租户 + 单账号，站点等为查询条件）
              ↓ 统一业务序列化 + 秘密移除 + 来源/版本/完整性
           本地业务副本

AI 建议 → 待审批草稿 → 人工审批 → 云端执行任务
              ↓ 云端重新校验原始用户、账号、审批、revision 和授权
           云端 Amazon API → 执行结果 → 本地副本/审计
```

读取通过条件：当前身份有效、当前用户仍拥有请求账号、账号所属租户匹配、相应 Amazon 官方授权和数据访问条件有效。满足条件后，所有已接入业务域使用同样的账号读取资格。

SP-API 与 Ads 的官方授权、Profile 和站点绑定仍须分别核实；不能由 SP-API 已授权推断 Ads 已授权，但这不是再次给 ERP 用户分配广告权限。查询不逐次调用 Amazon 做 OAuth；本地使用云端同步的可信授权状态和有效性证据。已知撤销/失效明确报错，状态过期或无法确认明确报“授权状态待确认”，不返回伪空结果。

所有业务查询必须明确一个 sellerAccountId；批量 ID、遗漏账号、伪造账号、外键指向其他账号均拒绝。账号列表仅返回当前用户可选账号的元数据。跨账号汇总、分页与导出不允许借省略条件绕过。

## 4. 分阶段实施

### P0：确认身份、账号映射与兼容清单

- 核对现有 SellerAccount 与真实 Seller ID、SP-API authorization、Ads Profile 的关系；accountKey 或名称不能作为真实身份依据。复用现有主键，不按 ERP 用户复制账号数据。
- 列出 Amazon ERP API、MCP 工具/别名、Lili 会话及 OAuth、分页、导出下载、缓存、后台分析任务的授权入口和对应测试；只覆盖本次相关路径。
- 出具旧个人授权、角色授权、管理员隐式访问、个人凭证的只读影响清单。确定迁移前后每个用户的账号范围，先处理冲突再切换。
- 账号分配复用 AmazonDataAccessGrant。角色只用于管理/审批职责；旧角色账号授权如需保留访问，须经审阅转为明确用户账号分配，不能给所有管理员自动补全账号。

交付：入口矩阵、账号映射证据、迁移预览及权限变化清单。此阶段不运行真实迁移。

### P1：统一账号读取资格

- 在现有 `data-access.ts` 中明确区分账号读取检查与管理/执行检查；不得全局删除 assertAmazonAction 或 assertAmazonScopeAdmin，因为同步、审批、凭证管理仍引用它们。
- Amazon 业务读取停用 mcpEnabled、tools 清单、模块 view、actions.view/export、marketplaceIds 和财务管理员等额外门槛。读取用导出同样继承账号分配；写入、配置和审批继续使用各自现有控制。
- 将“管理账号的资格”与“能读取全部账号”解耦，移除业务查询的管理员 allSellers 旁路。
- 服务端从认证上下文确定 actor；参数中的 userId、角色、sellerAccountId 及 approved 布尔值不能构成授权。
- ERP 内嵌 Lili 使用当前会话进入相同网关；外部 MCP/OAuth 保留 Token 生命周期、PKCE、resource 校验、撤销、刷新重放保护。Amazon 官方 OAuth 与客户端登录 OAuth 在 UI、错误和审计中分开命名。
- tools/list、实际调用与技能可用性使用同一结果；账号新增分配后无需重发字段/工具授权，账号撤销后旧 Token 不再赋予访问。

交付：普通成员仅分配账号即可经三种入口读取该账号所有已接入域，未分配账号稳定拒绝。

### P2：完整业务字段与共享查询结果

- ERP API、原生 MCP、Lili 共同调用现有查询服务和序列化器；移除 MCP 自有的第二层业务字段裁剪。优先整合现有 Ads 查询实现，保留兼容入口。
- 默认结果可返回适合分析的结构化字段；提供同账号、同权限的业务详情/扩展字段和原始业务记录读取路径，保证实际已存业务字段可取得。不得靠默认摘要永久隐藏其他字段。
- 复用字段注册、Schema 版本和原件证据。未来/未知字段保留原件并提供扩展数据及 Schema 状态；未映射、类型异常、解析失败分别说明，不标成“无权限”，不静默删除。
- 原始归档维持加密及摘要、来源、页/行号。原始业务内容读取在服务端处理，绝不把 OAuth Token、密码、内部密钥、含秘密的请求头或内部密文直接交给 AI。秘密移除是固定系统规则，不做逐用户字段配置；嵌套及扩展数据同样处理。
- 对可能受 Amazon 官方限制的内容核实官方数据条件，不能用新增 ERP 字段授权替代，也不能以“取消字段权限”绕过官方限制。
- 同账号内无法归属站点的财务记录保留未知归属语义，可在账号级证据查询中说明；无法证明账号/租户归属的隔离内容仍不得返回。站点筛选不能强行填造归属。
- 保留分页、日期窗口、行数/体积上限及限流，通过分页完整取得数据，不默认把完整 payload 塞进每个列表或 AI 上下文。截断必须提供标记和继续读取方式。
- 区分未接入、未同步、部分发布、字段未映射、已查询无匹配数据、账号拒绝和官方授权异常；不能将 NOT_IMPLEMENTED/未发布状态包装成用户缺权限。

交付：各域字段对照、广告 payload 差异修复、扩展/原始业务记录读取路径及秘密泄漏回归。

### P3：云端执行与本地完整副本

- 定向核查现有同步、Worker、凭证存储、复制和任务交接能力，再补齐差距；当前没有通过本轮调查证明完整云地链路已经存在。
- 正式 SP-API/Ads OAuth、刷新、发现、同步、回补及广告写入只在云端执行。本地保留业务数据完整副本，秘密凭证不随副本分发；本地请求正式 Amazon transport 必须在出站前被阻断，不能仅隐藏按钮。
- 复用现有 Repository、任务/Outbox、检查点及 Worker 管理体系，定义云地增量协议：稳定账号身份、版本/序号、幂等、删除/撤销事件、校验摘要、失败恢复和副本水位。复制原始业务证据时不得复制运行凭证；如需本地解密业务归档，明确独立的归档密钥管理。
- 用户及账号分配指定唯一权威来源，本地不得维护另一套可独立扩权的权限。撤销事件提交后，所有入口、缓存和导出立即按新状态拒绝；云地权限状态未确认同步时拒绝相关读取，不声称最终一致复制能保证即时撤权。
- 本地数据可有可见延迟并返回水位；授权变化不能复用旧数据缓存绕过检查。分页后续请求、已有下载链接、长连接及排队任务均重新检查账号。已交付给客户端的旧数据无法追溯收回，验收“立即撤权”针对撤销提交后新的访问/交付。
- 不因拆分直接停止现有 Worker 或移动凭证。先提供目标环境、现有任务清单、切换和回滚步骤，获真实操作批准后再执行；云端未接好前不能把本地查询失败解释为数据为空。

交付：云地职责门禁、可恢复复制、授权撤销传播及断网拒绝测试，证明本地正式 Amazon HTTP 为零。

### P4：广告人工审批与云端真实执行

- 复用现有 AmazonActionAudit / approvals / 草稿，补齐真实账号→Profile→实体绑定和云端 transport；普通竞价以固定明细批量审批，高风险动作逐项确认。
- 审批绑定提交人、账号、动作参数、旧值/新值、明细摘要、revision、有效期和幂等键。参数或实体范围改变后旧审批失效。
- 云端受信认证本地任务来源，并重新校验原始用户账号分配、人工审批、有效授权及实时实体条件；服务身份不能代替用户授权。已撤权或审批过期的任务不执行。
- 处理部分成功和结果未知，先对账再决定重试；只有 Amazon 结果确认的实体可标为成功。记录云端任务 ID、逐实体结果、执行时间及审计，回传本地。
- 真实执行未实现或未受控验收时继续明确 NOT_IMPLEMENTED，不宣称验收第 12 项通过。

交付：云端写入闭环。P1/P2 读取交付可先独立验收，不能替代 P3/P4 完整验收。

## 5. 数据与界面兼容

- 首轮不删除旧列/旧凭证/授权审计，不重建业务数据。旧读取限制列先停止参与新规则的读取判定；旧凭证只保留有效身份含义，不再冻结 Amazon 读取范围。写入/外部研究的旧配置不得随之失效。
- 既有角色授权和管理员隐式范围必须先做影响预览；无明确用户分配的不自动扩权。迁移前记录角色成员关系及授权 revision，迁移事务中重检，避免预览后成员变化造成误分配。
- “店铺与授权”中的读取配置收敛为用户—Amazon 账号分配；显示 SP-API/Ads 官方授权状态和副本新鲜度。移除逐域、逐字段、广告 MCP 读取开关；写审批保留独立入口和风险提示。
- 新旧读取策略按组织/环境原子切换，ERP/MCP/Lili 同时生效；不新增长期双权限模式。需要时兼容旧工具名和响应稳定字段，新增 schemaVersion、扩展字段和明确错误语义。
- 同步更新 `docs/amazon-agent-boundaries.md`、自动同步相关章节、Lili 说明及界面文案；旧“财务仅管理员”“单独启用 MCP”等规则标明被替代。AGENTS 仅维护原则及专项文档链接。

## 6. 验证与验收

先运行隔离测试，不加载真实 `.env` 或凭据。扩展现有 MCP、财务、Ads 查询、Lili OAuth 与集成测试，重点验证：

1. 普通用户 A 只有账号 A 分配，无 mcpEnabled、工具/域/字段授权，所有已接入域与 Ads 读取均通过。
2. A 访问 B、修改 seller/profile/source/run/report/export ID、复用 B 的分页游标均拒绝；管理员未分配 B 时也不能业务读取 B。
3. 撤权后旧 Token、缓存命中、后续分页、导出下载、长连接新调用、排队写任务失效；云地断连不沿用过期授权。
4. 官方授权已失效、尚未接入、未同步和真实无匹配数据得到不同结果；查询不触发 Amazon OAuth 或正式 API 请求。
5. 固定字段、嵌套字段、未知新增字段、原始业务内容保持可追溯；秘密、请求认证头及跨账号内容不泄漏。
6. Ads 已接入能力如实返回；SB/SD 或某报表尚未接入时标明能力缺口，不用 fixture 假装全量支持。
7. 人工审批缺失/过期/被修改、提交人撤权、账号混合、重复请求、部分成功及未知执行结果均按合同处理。

权限/共享逻辑实施阶段运行相关测试与 `npm run check:fast`，涉及模型再追加隔离迁移验证；合码前完整 `npm run check` 和 `git diff --check`。本轮纯规划只检查文档及 diff，不运行应用测试/构建。

真实验收另行确定环境、用户 A/B、真实账号 A/B、已接入域和受控竞价明细；实际迁移、云端调用/发布及真实写入仍分别按具体操作批准。记录必须分开：

| 验收记录 | 必须包含的证据 | 当前状态 |
| --- | --- | --- |
| ERP 查询 | 普通用户会话、账号、查询/拒绝、字段、撤权、官方授权错误 | 未运行 |
| 原生 MCP | 该用户个人凭证、协议调用 ID、工具/参数、结果/错误及审计关联 | 未运行 |
| Lili E2E | 当前用户/设备身份、实际工具调用链、结果及相同账号范围 | 未运行 |
| 云端广告写入 | 人工审批、云端任务与执行主体、授权复查、Amazon 逐实体结果 | 未实现闭环/未运行 |

用户提出的 12 项验收逐项对应上述记录；字段完整性须针对实际已采集 Schema/原件对照，不以少量样例或字段目录证明全部数据。缺数据/缺授权环境的项记录阻塞，不算通过。

## 7. 影响、风险与回滚

这是共享权限与跨模块变更，影响 ERP/MCP/Lili、财务、Ads、导出缓存和云地运行职责。实施前以本文及 P0 清单确认实际影响，不能只改 MCP 开关。
