# Wimoor 全量业务融合与企业级 ERP 移植计划

日期：2026-11-11。目标分支：`codex/amazon-multistore-mcp`（本次已核对）。

本计划替代原“SP-API 业务逻辑移植计划”，扩展为约 30 人公司内部 ERP 的业务融合路线。保留原文件路径，避免形成两份相互冲突的实施顺序。依据为用户提供的《Wimoor 743 表 + 14.2 万行 Service：ERP 全量融合与企业级升级任务书》。

**当前研究与融合状态（2026-11-11）**：本计划已由源码证据索引、13 个字段/模型/API/调用工作簿、公式首批证据及本地 P0-B WMS 实施验证补充。计划正文中的历史“尚未生成/未实施”描述仅反映早期 P0-A 写计划时状态；当前准确入口与域级判断见 [Wimoor 研究入口](wimoor-integration/README.md)，P0-B 状态见 [verification.json](wimoor-integration/verification.json)。本地实现使用合成隔离数据；没有真实库迁移、Amazon/MCP 连接、真人仓库或生产验收，也没有提交、推送或部署。

## 1. 融合原则与范围

采用现有模块化单体，沿用 Next.js、TypeScript、Prisma、PostgreSQL、BullMQ、Redis、Outbox、现有 SP-API/Ads Adapter 和 MCP Gateway。移植 Wimoor 的业务语义、字段关系、规则和流程，不搬整套 Java/Spring/MyBatis/MySQL/Quartz/Nacos 架构，不另建同步引擎或 MCP 查询系统。

全量研究与选择性建设分开：Wimoor 全部表、Service、Mapper、Controller、定时任务、API 和页面进入证据目录；目标 ERP 只实现已确认适用的业务能力，不按 743 张表一对一生成 Prisma 模型。企业采购、WMS、FBA 头程、成本、应收应付、总账、组织审批纳入路线，原 SP-API 报表补差保留为数据中心子工作项。

每项先判定“复用、补充、新建、重构或排除”，再实施。复杂流程采用领域规则、Application Service、Repository、状态机和 Outbox；普通 CRUD 沿现有方式，不机械加层。共享模型、权限、存储、Worker 或多模块变更，在每批实施前说明具体影响、验证和回退范围，并遵循仓库确认边界。

## 3. 第一批：建立可追溯的全量证据目录

规划输出位置：`docs/wimoor-integration/`。本轮不生成空壳 Excel；后续使用可重复运行的提取脚本生成真实内容，记录输入文件、解析错误、未覆盖语法和提取器版本。

SP-API 从用户指定本地指南 `/Users/chenjieliang/Desktop/亚马逊官方文档 SP-API新人配置指南.md` 进入，核对可用的官方 OpenAPI 文件。任务书要求的“最新”在取得对应官方资料前标记待核实：保存 Schema 来源、版本、获取日期、SHA-256 和 Operation 证据，不能用 Wimoor SDK 或版本号代替。缺少 Schema/文档或资料冲突时记录具体缺口；需要在线核实时遵循用户另行明确的在线查证范围，本轮不自动抓取官网。

## 6. 业务边界与核心不变量

### 6.1 商品与库存

ProductRecord 继续为商品核心资料唯一事实源。公司仓库存、Amazon FBA 库存、在途、采购未到货独立表达；SKU/ASIN 文本相同不证明跨账号、站点或组织是同一库存实体。Amazon 和 Sellfox 快照保留来源，不直接变成公司仓库存流水。

WMS 分两步建设：先多仓/区域/库位、SKU/批次/条码、收货/质检/上架、预留/释放/冻结、拣货/出库、流水和余额；再退货、移库/调拨、调整/报损、盘点/差异审批、快照和预警。“四级盘点”的层级、流程和权限先从源码及公司实际需求核实，不猜测为四种库位或四层审批。

每次库存变化具备数据库事务、唯一流水号、业务幂等键、revision，以及条件更新或行锁；不允许应用先读后无条件加减。拒绝不符合策略的负可用库存，冻结/预留与实物余额分别校验。跨库调拨包含发出、在途、接收及异常恢复，不伪装为两个无关联加减操作。验证余额与流水一致、重复请求不重复扣减、并发预留不超卖、撤权不能写入。

### 6.2 FBA 头程 V2

以 Fulfillment Inbound `v2024-03-20` 官方 Schema 为目标，逐 Operation 核实支持范围。保留现有只读采集，新增写工作流在独立应用服务和审批边界内衔接。

覆盖：Inbound Plan/Items → Packing Groups/Boxes/Box Items → Packing Options/Confirmation → Placement Options/Confirmation → Shipments → Transportation Options/Confirmation → Delivery Windows → Labels/Tracking/Events → 入仓及差异对账。各步骤区分内部草稿、待审批、外部处理中、确认成功、失败和结果未知；Amazon 状态与内部物流状态不共用含混枚举。

保留原始请求/响应、API 版本、Operation、Request ID、时间、幂等键、错误和文件摘要；敏感载荷走既有受控归档，不回传业务查询。写前校验当前用户、Seller/Marketplace、revision、批准范围和有效期。异步结果按 operation 轮询/回读，结果未知先核实，不盲目重复创建或确认。

报关 XML、报关单和附件独立建契约与验证，不假设 Amazon 提供完整出口报关接口。闭环为商品/公司库存 → 计划 → 装箱 → 分仓 → 运输 → 发货 → 入仓 → 差异对账；本地仅模拟外部写操作，真实执行另行批准。

### 6.3 采购、成本、应收应付与总账

P1 建采购单、收货/退货、付款、物流费用、交易标准化、应收应付和分摊链；支持部分收货、部分付款、取消、冲销和来源关联，不以采购未到货量充当可用库存。

P2 建会计科目、期间、凭证/明细、总账/明细账、余额、银行流水、对账、结账、反结账和审计。金额/高精度采用明确字符串契约与精确计算；原币与本位币分开，记录汇率来源/日期、精度、舍入及分摊余差规则。费用可追溯订单、SKU、采购或物流单，凭证可追溯源单。

约束包括借贷平衡、源交易幂等、期间锁定、已过账不可直接删除/改写、冲销留痕、反结账审批；重复导入不重复入账。Amazon 交易、结算、费用估算和实际费用分清，财务报告不能未经审核直接过账。

### 6.4 企业管理、查询与 AI

沿现有组织/成员/角色扩展部门、员工岗位、单据编号、文件、配置、导入导出、任务、通知、操作记录和经营仪表盘。P0 即具备关键库存/FBA 写动作需要的权限、审批和审计，P2 再整合审批中心、异常中心页面，不能等到 P2 才保护写操作。

ERP 业务操作权限与 Seller Account 读取授权分开。ERP、原生 MCP、Lili 复用同一服务端查询服务；每次 Amazon 查询明确一个账号和站点，服务端实时校验分配及撤权，不新增字段/数据域/API 级读取授权，不由 MCP 直接写任意 SQL。P3 AI 输出建议/草稿，经人工批准、服务端校验执行并回读结果，AI 不直接过账、扣库存或修改 Amazon。

持续保护项：已实现同步适配器继续使用统一发现、计划、历史覆盖、增量、恢复和发布管道。历史缺口以实际已发布完整区间计算；已归档优先复用，解析/入库/发布失败从原任务恢复；不因新增 WMS 或 FBA 写流程改变云端唯一正式 Amazon 执行端。新增账号继承规则、新适配器自动进入生命周期仍为回归要求。

## 8. 字段映射与数据迁移

按 WMS、FBA、财务交付字段映射和 `prisma-model-mapping.xlsx`：源表/列、源类型、目标模型/字段、含义、关系、身份范围、单位、精度、空值、转换、默认规则、历史保留、来源证据、冲突及决定。目标模型名须经现有 Schema 对照后确定，本计划不把拟建名称宣称为现有模型。

迁移分开处理：本 ERP Schema 增量迁移、业务规则移植、可选旧系统业务数据导入。未确认有旧业务数据迁移需求时，只移植规则和必要结构；不把 Wimoor 初始化 SQL 或全部 743 表导入当前数据库。

需导入时先明确组织/工作区/账号/站点映射、主键重映射、外键、SKU 身份、币种、时间区、重复和未知字段处理。提供 dry-run、批次幂等、检查点、异常隔离、数量/金额/库存对账及来源证据。密码、Token、Redis 数据和真实凭证不纳入移植。

迁移在明确创建的隔离空库、旧版隔离种子升级库分别验证；验证重复执行不重复写入，失败能恢复。生产迁移必须独立批准并走现有 CI artifact/deployment-plan。回退以本批应用改动和明确的前向修复为主，保留已发布事实、库存流水、财务凭证、任务和原件，不自动执行降级删表或整文件回滚。

## 9. 验收证据与性能门槛

| 层次 | 必须验证的行为与记录 |
| --- | --- |

| 云端真实 Amazon | 本地模拟通过后单独批准部署/迁移/重启和联调。只由云端执行；只读与真实写分别审批验收，记录资格、请求、业务结果、发布、查询和结果回读。 |

隔离环境不加载根 `.env` 或继承真实凭证，Amazon transport 只允许受控模拟端点；验证目标身份后才启动临时资源，不连接生产队列或领取正式任务。现有共享文件禁止整文件覆盖/恢复，不改变真实配置。

性能分当前日常基线和增长容量两档：约 30 员工、多卖家/站点，并用明确的 SKU/流水/广告记录量、行宽、数据分布、并发数、批量大小和 Worker 数定义压测。先测基线并确认目标，再报告 P50/P95、吞吐、错误率、锁等待、队列延迟、数据库/内存/IO；本轮不承诺未测数值。重点覆盖大批导入、大表分页、多人修改、并发同步、重复任务、重建和撤权。

优先索引、分批、游标分页、必要 Projection/Outbox、按范围缓存及虚拟表；读写分离先明确主库事务与派生读模型的职责和一致性，不默认新增只读副本、Kafka、微服务或分布式数据库。性能/资源改动超过现有边界时先说明测量结果和替代方案。

状态分开记录 CODE_IMPLEMENTED、TEST_VERIFIED、REAL_DATA_VERIFIED、ERP_QUERY_VERIFIED、MCP_QUERY_VERIFIED、SKILL_E2E_VERIFIED，并附环境、数据来源、时间和证据；本地模拟不能升级为真实 Amazon 验收。
