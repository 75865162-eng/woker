# Amazon Ads 下一阶段升级计划（代码核对版）

日期：2026-11-06。状态：规划建议，尚未批准实施。

实施进度追加：用户随后要求“开始编写”。U0 首批本地能力清单、只读 CLI 和真实 SQL 链的隔离迁移验收已交付，见 [U0 交付](./amazon-ads-u0-delivery-2026-11-06.md)；原类型阻断已被工作区其他改动修复，当前全仓 TypeScript 通过。下一批共享行为的具体范围见 [U1 实施方案](./amazon-ads-u1-implementation-proposal-2026-11-06.md)。本条不表示真实采集、配置、任务、迁移或部署已获批准，也不改变下方原始审计时的验证记录。

依据：用户粘贴的《Amazon Ads 后台负责提供数据和执行接口……》、当前本地工作区代码，以及 Phase A–D、真实 Profile 准备和升级规划的交付记录。本文件不替代已有交付历史；历史文档与当前代码不一致时，以本次标明的代码证据及验证范围为准。

## 1. 结论与近期目标

当前已经有一套可复用的 Ads 读取、存储、查询、权限与 MCP 基础，不需要从 Campaign transport 或四层架构重新开始。主要差距是：真实报表采集尚未实现、结构历史与原始证据留存不完整、主要业务页面与真实数据查询仍分离、正式广告写执行没有接通。

下一阶段应交付一个业务上可验收的只读切片：

**一个组织/工作区、一个获批 Profile、SP Campaign 结构和一种 Campaign 日报，经过原始证据留存、标准化、版本发布、数据库查询，进入 Campaign 页面和同口径 MCP，并能追溯来源。**

先用隔离 fixture 交付整个切片；真实账号验收作为独立批准后的闸门。不能将离线通过、adapterReady 或数据库中存在记录当作真实 Amazon 采集成功。

## 2. 当前进度：哪些可以复用，哪些没有完成

| 能力 | 当前本地代码 | 仍缺什么 |
| --- | --- | --- |

| 报表发布 | staging、校验、原子发布和撤回恢复已有隔离实现 | `report-publication.ts` 明确受 `ISOLATED_FIXTURE_ONLY` 与离线环境闸门限制，不能直接用于真实报告 |
| 页面 | 默认进入已同步数据页；可查实体/日报、筛选分页、范围汇总；账户页显示任务状态 | Amazon 风格的 Campaign → Ad Group → 投放业务页面仍主要使用 Demo；不能说全部页面已切换真实数据 |

| 规则 / 草稿 / 审批 | PPC 规则、Bulk 导出和 Agent approval/audit 边界可复用；Ads 已有 dry-run plan | Ads 页面、MCP 与持久草稿统一接线，精确对象 ID、证据版本及审批绑定 |
| 正式写入 | Ads 客户端保留合同校验与阻断，正式 HTTP 写 transport 未实现 | 逐操作官方合同、执行幂等、未知结果对账、回读验证和逆向草稿 |

关键证据：

- 结构范围：`src/lib/amazon-ads/sync-adapter.ts` 的 `createSponsoredProductsReadAdapter` / `verifiedAdsReadStages`；reports 阶段仍抛 `ADS_REPORT_ADAPTER_NOT_IMPLEMENTED`。
- 当前快照：`sync-processor.ts` 对 `AmazonAdsEntityRecord` 按业务键 upsert；`payload` 更新不能证明旧版本或完整原始 HTTP 响应已保留。
- 报表发布门槛：`report-publication.ts` 的 `offlineOnly`、manifest evidence 和 `COMPLETED_ISOLATED_REPORT`。
- 正式查询：`query-service.ts`、`report-query.ts`、`repository.ts`；页面与 MCP 应继续共用这些服务。
- 页面模式：`ads-workspace.tsx` 默认 `synced`，独立 `AdsSyncedData` 可用；Demo 分支仍导入 fixture/mock provider。
- 写执行：`src/lib/amazon/ads-client.ts` 没有真实 HTTP transport；`amazon-action-audit.ts` 仍返回阻断/dry-run 结果。

以上是本地工作区结论，不代表 GitHub、持久数据库或服务器已经包含这些修改。本次没有读取远端或生产状态。

## 3. 对原文建议的调整

1. **保留八个方向，但避免重建已有基础。** Raw / Normalized / Facts / Read Models 是逻辑职责，不要求建立四套系统。继续使用 PostgreSQL、现有 storage adapter、队列和查询服务；不为了分层引入新数据库或缓存。
2. **完整覆盖是最终目标，第一轮应限定 SP。** P0 交付一个完整切片；SP 核心实体/报表覆盖作为后续扩展。SB、SD 分别建能力矩阵；DSP 单独立项。
3. **数据质量与来源属于 P0 验收。** 它们直接决定 AI 能否使用数据，不能等全部 UI 完成再补。CURRENT 只表示当前实现中的状态，不等于完整日期覆盖或归因已最终稳定。
4. **把结构历史提前到正式优化之前。** 日报有版本不等于广告对象有历史。必须能证明建议生成时的竞价、预算、状态和归属，执行前还要核对远端现值。
5. **不按固定示例阈值直接上线规则。** ACOS 区间、点击阈值、预算幅度、回补天数均需结合利润、生命周期、币种、广告产品、归因及延迟验证并配置化。
6. **暂不一次增加十二个一级页面。** 保留现有入口与深链，优先接好 Campaign、投放、搜索词、优化草稿和变更中心；同步与 MCP 管理先扩展既有面板。

## 4. 实施路线与交付闸门

### U0 / P0：收口当前基线与能力清单

范围：现有 Ads/MCP 改动、测试、文档、增量 migration，不扩展广告产品。

- 盘点整个工作区，区分已有实现、未跟踪代码、生成目录和其他规格；明确待提交范围。不得自动清理、stash、提交或推送。
- 修复当前类型检查阻断，再补齐适用检查；旧交付记录的通过结果不能替代当前工作区基线。
- 在一次性隔离数据库验证实际 migration 链：空库安装、旧基线升级、历史 nullable/legacy 数据与跨 Profile 约束失败情形。`db push` 测试不等于 migration 验收。
- 整理逐数据域能力清单：SP/SB/SD、官方端点与版本、读取/写入、字段/日期/归因限制、账号权限、本地留存、UI、MCP、离线测试和真实验收状态分别记录。未知项写待核验，不提前给支持承诺。
- 整理文档中仍称“reader 未接 worker”“所有页面均 Mock”等旧描述，保留历史并明确最新状态。

验收：明确的本地变更基线、可通过的相关检查、实际 SQL 迁移验证结果，以及能区分代码/合同/账号/产品可用性的矩阵。

### U1 / P0：完成 Campaign 结构＋一种日报的离线纵向切片

范围：现有 `amazon-ads` 模块、storage adapter、同步 worker、查询 API、Campaign 只读页面及现有 MCP 工具。

- 锁定一种 SP Campaign 日报的真实官方合同：API 产品与版本、reportType/query、维度、字段、日期限制、归因、时区、币种、空报告、warning 与删除/覆盖语义。通用 Reports 信封 parser 不能替代具体报告合同。
- 实现 create → poll → download → 解压/解析 → staging → 校验 → 发布，并保留中间状态/checkpoint。按实际所选 API 合同执行，不预设必须使用现有 v1 信封。
- 原始请求参数、报告 ID、响应/报表文件、内容校验、采集时间及来源任务形成可追溯链；二进制经 storage adapter / FileObject，禁止业务层依赖 uploads 物理路径。临时 URL 与 token 不进入日志或 MCP。
- 下载需校验允许目标、重定向、过期、字节/解压/行数上限和全部分片；任何失败不发布不完整版本。
- 将正式发布路径与离线 fixture 声明明确区分，复用事务、fencing 和校验规则；不得删除离线闸门后直接把 fixture manifest 当官方合同。
- 对相同事实保留历史修订，查询选最新有效发布版本；迟到数据重采生成新版本。明确空报告及旧事实消失时的行为，未经合同确认不能推断归零或永久保留为当前事实。
- 将 Campaign 列表和日报指标接同一查询边界；汇总按完整筛选范围计算，保持货币/归因口径分组；MCP 返回同样的来源、版本与新鲜度。
- 增加 create/poll/download 分项预算、最大运行时间、重试上限、存储限制和暂停恢复。优先日批及有界窗口回补，不默认全历史高频同步。

验收：fixture 从 worker 到存储、页面、MCP 的完整闭环；重复/乱序/失败/部分分片不产生伪成功；第二次修订可追溯且不重复累计；不同 Profile 隔离。此时仍不得宣称真实数据接通。

### U2 / P0：一个获批 Profile 的受控只读验收

依赖：U0/U1；已有 `amazon-ads-test-profile-readiness-2026-11-06.md`。

- 明确目标环境、组织/工作区、店铺/站点、授权/Profile 标识、区域、币种、时区与精确写入范围；提交脱敏配置 diff、命令、预算、停止条件及恢复方式。
- 结构 worker 实际遍历八类 SP 对象，不能将当前运行方案写成 Campaign-only；若要限定单域，须先实现并离线验证持久化范围限制。
- 结构测试和日报测试分别写清请求范围。已有准备文档中的结构候选预算不自动适用于 Reports create/poll/download。
- 只在用户批准对应真实请求和目标配置后执行。先完成小窗口，核对上游范围、落库记录、页面和 MCP；空结果如实记录，不用 fixture 补齐。
- 对 401/403、Profile/区域不符、未知响应、越预算或权限变更立即停止，保留 checkpoint。应用回滚不删除采集数据。

验收：真实只读采集记录、同口径抽样核对、页面/MCP一致、可追溯版本与完整性说明；不能把有一条数据理解为整个 Profile 已全量覆盖。

### U3 / P1：扩展 SP 结构、报表与业务页面

按业务依赖依次扩展，每次只交付一个可验收数据域：

1. Product Ad 结构和广告商品日报，补齐 Campaign → Ad Group → Ad → SKU/ASIN 关系。Advertised Product 报表不替代 Product Ad 对象同步。
2. Keyword / Targeting 表现和 Search Term，明确搜索词、触发关键词、定向表达式、匹配类型与作用层级；不能直接把搜索词当关键词 ID。
3. Placement 表现，支持按 Campaign/日期/广告产品正确分析，未知归因字段保持空值。
4. 将既有八类结构查询接入 Ad Group、Keyword、Target、Negative 页面；保留 Demo 明确入口及现有深链兼容。
5. Portfolio 和额外 Budget/Bidding 设置按实际优化需求补齐；Campaign 级否定对象已有结构读取，不重复作为从零开发项。

同步补齐每域最后成功、日期缺口、历史起点、来源任务、记录数、失败/警告和 MCP 可用状态。仅 MIN/MAX 日期不能证明中间没有缺日；只有合同允许时才期待每日都有行。

验收：每域同时有合同、采集、查询、UI、MCP 和质量证据；无权限/无覆盖/未同步/空结果/零指标分开显示。开始正式优化前完成相关对象的历史观察版本或等价不可变证据，保留当前快照作为快速查询层。

### U4 / P1：用真实证据生成统一优化草稿

范围：复用 PPC 规则引擎、Workspace 草稿、Bulk 导出及 Agent Gateway 审批/审计，不另起审批事实源。

- 首个业务场景：按 Profile、日期、币种，查询花费超过用户阈值且无订单的搜索词/投放对象，按点击排序，关联当前结构，生成候选建议。
- 阈值与动作由可配置策略决定；订单归因未成熟、上下文不完整或数据过期时，给出限制并阻止不安全动作。不能仅凭花费无订单自动判为应否定。
- 草稿保存稳定远端 ID、作用层级、before/after、来源事实版本、结构观察时间、策略版本、理由、风险、创建者、revision 与幂等键。
- UI 与 MCP 共用草稿服务；规则与 AI 的冲突先模拟并显式处理；审阅支持逐项接受/拒绝，审批绑定精确 revision/digest/范围/有效期。
- 先交付预览、审批和经校验的 Bulk 文件导出。导出只证明文件已生成，不表示已经上传或 Amazon 已接受，外部应用状态必须单独记录。

验收：同一输入可追溯并解释；撤权、过期、草稿修改或对象变化会阻止应用；原始 workbook 不变；AI 不绕过人工审批。

### U5 / P1：统一 API / Bulk 变更执行与回读

依赖：U4；每种写操作和真实启用均单独评审批准。

- 统一草稿/审批/执行记录，适配经验证 API 和 Bulk 文件渠道；保留已有 Bulk 能力。
- 首个 API 写切片只选择一种操作，例如 SP Keyword bid；预算、状态、否定词和 Target 逐项新增合同及验收。
- 应用前核对权限、Profile、审批摘要、有效期、远端现值、竞价/预算护栏、重复操作和频率。
- 执行记录逐项成功/失败/未知。超时结果先回读对账，禁止盲目重试写入；用持久幂等和任务状态防止重复提交。
- 写后回读确认，再显示已生效；保留 Amazon 响应安全摘要与审计。Bulk 人工上传也需要结果导入/匹配与回读，不能只记录“文件下载成功”。
- 恢复使用新的逆向草稿，重新校验当前值并审批；不承诺任意动作可撤销，不自动覆盖 Amazon 上的后续人工操作。

验收：未经审批无写请求；模拟超时/部分成功可恢复；结果未知不会重复写；已生效有回读证据；故障可停用执行器并保留历史。

### U6 / P2：高级优化和其他广告产品

在 SP 事实与变更闭环稳定后，再按业务收益扩展 SB/SD、跨店铺分析、预算分配、异常监控及自动化策略。

跨店铺不合并不同币种/时区/归因口径；TACoS 依赖同范围总销售额，不能用广告销售额替代。库存、Buy Box、利润联动须有同范围权威数据和更新时间。Creative/Brand 按账号实际可用能力接入。DSP、流式系统和新数仓不默认纳入。

## 5. 数据与性能设计约束

- ERP 服务端 PostgreSQL 是共享 Ads 数据持久层；“本地仓库”不意味着偷偷复制到每台电脑或改用 IndexedDB 保存共享事实。
- 四层职责优先复用现有 EntityRecord、ReportVersion/Fact、Request/Document、FileObject、DomainState 和查询服务。历史结构证据如需新增 schema，先评审最小方案，不为每个域复制一套表/服务。
- 实体 payload 当前覆盖更新，不能承担不可变 Raw 层；需要按任务/页面或内容哈希保存原始证据与历史观察，定义存储保留、访问隔离及重建关系。
- 结构同步逐页可见与完整快照是不同语义。当前缺席不删除的安全行为保留；若引入全域快照发布或删除推断，单独评审一致性和数据成本。
- 原始文件与历史版本会增加存储；轮询、回补、最新版本去重/count/汇总会增加 API、数据库与队列消耗。实施前提交范围、配额、P95 风险、替代方案和验证计划，获得批准后再改。
- 优先服务端有界查询、分页、日批和复用查询；不因“完整数据仓库”直接引入 Redis/ClickHouse/微服务。先用隔离规模数据记录查询、发布、并发与恢复性能，再决定索引或缓存。
- 保留周期、撤权后的访问、组织关闭和备份过期需明确策略；不承诺无限保存，不擅自删除真实历史数据。

## 6. 推荐下一张实施单

建议下一轮限定 **U0＋U1 的官方合同与离线实现方案**，验收物为：

1. 当前类型错误修复及适用基线检查结果；工作区完整清单和 migration 验证方案。
2. SP 数据域能力矩阵，以及一种 Campaign 日报的字段/归因/日期/下载合同。
3. 复用现有 worker/storage/publication/query 的具体文件变更、性能影响、回滚与隔离测试清单。
4. 获批本地实施后，交付 worker → 原始证据 → 发布事实 → Campaign 页面 → MCP 的完整 fixture 场景。
5. 独立提交 U2 的目标账号、精确命令和预算审批单。

不建议下一轮继续只加一个 parser 就作为业务交付，也不建议一次铺满十二个导航页面。第一张实施单的产品完成标准是“同一份可追溯事实能从页面与 MCP 查到”。
