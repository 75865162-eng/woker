# 数据口径与可复现验收案例

日期：2026-11-06。状态：待评审设计，未修改现有查询或数据库。对应 T04/T12/T13；所有金额和对象均为模拟值。

## 1. 口径身份与时间

建议将“可比较口径”定义为：广告产品、报告类型、API 合同版本/digest、日期语义、报告时区、币种、归因窗口、指标定义。组织/工作区/店铺/Marketplace/Profile 始终保留，不能因为币种相同就视为同一业务范围。

- 报告日是合同约定时区的日历标签，不用 JavaScript UTC 日期转换重新分桶。采集、发布、审计时间保存绝对时间；展示时明确展示时区。
- 历史报告时区来自当次已保存证据。只有 Profile 当前时区而没有历史证据时记 UNKNOWN，不回填为“已核验”。DST 日可能不是 24 小时，不能用固定秒数推算当地日报区间。
- 日期语义如点击日、转化日须随合同确定；不跨语义直接拼接。API 版本更换需要字段映射和重叠期对账，不能只改 `apiVersion` 标签。
- 跨 Profile 比较默认分组。合并必须明确选择同口径范围，并能回溯各 Profile 的贡献；汇率换算属于额外派生结果，保存汇率来源/日期，不覆盖原币金额。

## 2. 三类状态分别表达

| 维度 | 规划值 | 说明 |
| --- | --- | --- |
| 范围覆盖 | UNKNOWN / OBSERVED / VERIFIED_COMPLETE / VERIFIED_EMPTY / PARTIAL | 有数据不等于完整；空结果须由合同及完整请求证据证明 |
| 新鲜度 | UNKNOWN / CURRENT / STALE / SYNCING / FAILED | CURRENT 只描述时效，不保证范围完整；新任务失败不销毁旧发布数据 |
| 归因成熟度 | UNKNOWN / PROVISIONAL / MATURE_BY_POLICY | 仅策略与证据支持时标成熟；策略成熟不等于 Amazon 承诺不再修订 |

这些是候选输出术语，不直接复用或修改现有枚举。质量说明同时返回依据、观察时间、合同/策略版本和原因码。不得把 FAILED、PARTIAL 和 UNKNOWN 显示为“0”。

## 3. 指标与缺失值

原始计数/金额继续以精确十进制字符串传输，null 表示未知/未提供，0 表示已知零。派生比率沿用 `metrics.ts` 的百分数点语义：CTR=clicks/impressions×100、CPC=spend/clicks、CVR=orders/clicks×100、ACOS=spend/sales×100、ROAS=sales/spend；分母零或任一输入未知返回 null。

现有 SQL SUM 会忽略 null：因此一组行中部分金额缺失时，结果仅是已知部分，不能自动认定完整总额。规划对每个指标返回 knownRowCount、missingRowCount 和 completeness；已知小计与严格总计分开表达。新增字段及接口名称待 T01/T04 评审，不在本文件声称已提供。

- 已知小计保留可用数值，并标 PARTIAL；严格总计在存在缺失时为 null。
- 即使全部行有值，如果整个请求范围未证实完整，仍不能称“整个范围真实总量”。指标完整性与范围完整性分别判断。
- 同组汇总后再算比率，不平均行级比率。用于可执行建议的判断必须同时满足口径、指标完整性、覆盖、新鲜度及归因策略。
- `orders=0` 且 `sales=null` 不等于 ACOS 无限大；不能自动变成否定或暂停操作。

## 4. 版本与替换案例

| 案例 ID | 模拟输入 | 当前已知行为 | 后续验收预期 |
| --- | --- | --- | --- |
| DC01 迟到修订 | 同 Profile/日/Campaign，V1 spend=10/orders=0；V2 spend=10/orders=1 | 按事实键选择最新发布值 | 当前不叠加两版；V1 保留可追溯，建议绑定版本并在 V2 后重新校验 |
| DC02 缺行 | V1 有 A=10、B=20；V2 只有 A=12 | 逐键选择得到 A=12、B=20 | 未证明完整时维持保守查询并标范围不完整；只有合同支持整范围替换时才评审 B 的排除语义，不推断 B=0 |
| DC03 空报告 | V1 有 A；V2 合法响应解析出 0 行 | 当前 parser 拒绝空报告 | 合同未核验时不发布、不清空；若支持 VERIFIED_EMPTY，需独立范围证据和版本选择设计，不能靠虚构零事实实现 |
| DC04 部分文件 | 预计 2 份，只有 1 份验证通过 | V3 当前仅单文件，不代表支持分片 | 对未来多文件合同，全部 part ID/数量/hash 完整才发布；任一缺失维持旧版可见 |
| DC05 重叠窗口 | V1=1–7日，V2=5–10日 | 当前按日/键最新值选择 | 不将两个窗口求和；若采用窗口替换，明确5–7日的裁决，1–4日不能随之删除 |
| DC06 乱序完成 | 较早请求迟完成，晚请求先发布 | 当前按 publishedAt/id 选择 | 决策必须确定“最新”依据；发布时间不证明上游观察更新。无上游修订序号时保守处理乱序，保留请求/生成/采集/发布时间与排除理由 |
| DC07 撤回 | 当前 V2 撤回，V1 仍有效 | 现有可见性机制可保留历史 | 根据选定规则回退 V1，并标已回退/可能过期；不伪造新鲜度或清除旧证据 |

DC06 是新增待决项：T04 应决定采用可验证上游生成时间、受限串行化或其他防乱序规则；不得把任意到达顺序当真值顺序。完整窗口/tombstone 模式仍未选定，不在当前逐键读取上偷偷叠加另一种模式。

## 6. 页面与 MCP 的兼容策略

现有 data API 和 `amazon.ads.reports.list` 保留既有分页、参数别名与授权检查。优先追加可选质量字段；若 totals 的含义或分组键改变，不能称纯追加兼容，必须采用显式响应版本/新受控分析入口，并先盘点页面、MCP schema、CLI 和 Skill 消费者。

过渡期旧 totals 按原语义保留并标限制，新质量统计提供独立完整性信息。普通只读历史可查看；优化草稿服务从服务器验证证据，不依赖客户端传来的“完整/成熟”标签。未知输出字段的旧客户端可忽略，旧客户端不能因缺字段被升级为可信分析。

现有查询排序稳定性、同快照 rows/count/totals、实时授权复查都必须保留。回滚必须能恢复旧读路径，不删除新增证据；历史数据无法重建时区/合同摘要的记录继续明确标记未知。
